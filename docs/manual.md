# ISUNARABE 合同演習2026 当日マニュアル

このマニュアルは合同演習2026 当日の運用 (環境構築・ベンチ走行・追試) を扱う。
競技そのもののルールはレギュレーションを参照。両者で食い違いがある場合はレギュレーション
が優先する。

## 1. スケジュール

- **12:00**: 競技開始
- **19:00**: リーダーボード上の他チームのスコア更新表示停止 (= スコア凍結。
  自チームのスコアは引き続き更新される)
- **20:00**: 競技終了
- **追試 / 結果発表**: 競技終了後、主催者が順次実施。完了タイミングは当日 Discord で
  アナウンス

合同練習会としての性格上、進行は柔軟に行う。タイムテーブルがずれる可能性がある。

## 2. ポータルと連絡手段

### 2.1 ポータル

競技は ISUNARABE2 ポータル上で運用される。

- ポータル URL: `https://isunarabe.org/` (ログイン後にコンテストページに進む)
- 主な機能:
  - 負荷走行 (ベンチマーク) のリクエストと結果確認
  - リーダーボードの確認
  - CFn テンプレート / マニュアル / レギュレーション URL の取得
  - 主催者からの全体アナウンス受信
  - 質問送信は提供されない (= Discord 上で行う、§ 2.2)
- 他のチームの妨害にならない範囲において、ポータルの API を直接呼び出す行為を制限しない

### 2.2 Discord

- 主催者からの全体アナウンスはポータルと Discord の両方を用いる。競技時間中はどちらにも
  気づける状態にしておくことを推奨する
- 質問の受付・回答は Discord 上で行う
- 競技時間中、主催者の判断で個別チームに対しプライベートチャンネルを切ってメンション
  することがある。応答可能な状態を維持してほしい

#### Discord サーバー
Channel 78.0 https://discord.gg/guZJJm4n

### 2.3 質問

- 質問は Discord の #isu-general で受け付ける
- 主催者の回答は原則として全選手に公開する。重複した質問やチーム個別の問題への対応は
  個別回答となることがある
- 競技性に影響を与える内容と判断される質問には回答できない場合がある
- 合同練習会としての性質上、運営は柔軟に行う。回答に時間を要する場合があることを
  了承いただきたい

### 2.4 サポート対象外

- AWS そのものに関する質問 (AWS アカウント / 課金 / クォータ等)
- AI ツール (LLM / コード生成サービス等) の利用方法に関する質問
- 各チームの開発環境固有のトラブル

## 3. 競技環境の構築

### 3.1 CFn テンプレートのダウンロード

ポータルの該当コンテストページから、チームに固有の CloudFormation テンプレートを
ダウンロードする (= テンプレートはチームごとに異なる。共有しないこと)。

このテンプレートで作成されるリソースは概ね以下:

- 競技用 VPC (`192.168.0.0/16`) と Subnet (`192.168.0.0/24`)
- インターネットゲートウェイ / ルートテーブル
- セキュリティグループ
- EC2 インスタンス x 4 (= ベンチマーカー兼ジョブ実行ノード x 1 + SUT x 3)
- EBS (gp3) x 4
- EIP x 4

正確なリソース構成・インスタンスタイプ・EBS サイズは配布される CFn テンプレートの
記述に従う。

### 3.2 スタックの作成

1. AWS マネジメントコンソールの CloudFormation を開き、リージョンが
   **アジアパシフィック (東京) (`ap-northeast-1`)** になっていることを確認
2. 「スタックの作成」→「新しいリソースを使用 (標準)」
3. 「テンプレートファイルのアップロード」を選び、3.1 でダウンロードしたファイルを指定
4. 任意のスタック名 (例: `isunarabe2026`) を入力
5. 作成。状態が `CREATE_COMPLETE` になるまで数分待機

### 3.3 サーバーへの SSH 接続

スタック作成完了後、数分でログインできるようになる。

- ユーザー名: `isucon`
- 認証: 選手が GitHub に登録している SSH 公開鍵 (= AMI 起動時に GitHub から取得され、
  `~isucon/.ssh/authorized_keys` に書かれる)
- 接続先 IP: ポータルのサーバーリスト、もしくは AWS マネジメントコンソールの
  EC2 ページから確認

EC2 Instance Connect でも接続可能 (ユーザー名 `isucon`)。

ポータルにサーバーが表示されない場合は EC2 Instance Connect でログインし、
isuwari (§ 6.1) のステータスを確認すること。

## 4. 競技環境の制約

### 4.1 変更してはいけないファイル / 設定

以下を変更したチームは失格となる (詳細はレギュレーション参照):

- `/etc/systemd/system/isuwari.service` および isuwari (= 追試制御デーモン) に
  関連する一連のファイル
- `/opt/isuwari/` 配下
- `isuadmin` ユーザのアカウント・権限・ログイン情報
- アプリケーションフロントエンドの静的ファイル (HTML / CSS / JavaScript / 画像)

### 4.2 変更してよい点

- DB スキーマ / インデックス / 初期データ (= `POST /api/initialize` で初期状態に戻せる
  範囲なら自由)
- ミドルウェア構成 (nginx / MySQL / アプリの配置・台数分担・キャッシュ層追加など)
- 参考実装の改変 / 破棄 / 別言語による書き直し (ただし参考実装は Rust のみ提供)
- セキュリティグループの追加開放 (ただし SSH 22 / HTTP 80 は変更しないこと。
  本問題は TLS を使わず、参考実装の webapp が直接 80 番で SPA + API を配信する)
- OS パッケージ・カーネル設定

### 4.3 計算機資源

- 競技に利用できるのは CFn で作成された 3 台の競技用サーバーのみ
- インスタンスタイプ変更 / 台数追加・削減 / リージョン変更は失格
- モニタリング・テスト・開発のために外部リソースを併用するのは認めるが、
  **スコアを向上させるいかなる効果も持つもの** は認めない (= 外部キャッシュ・
  外部 LLM 呼び出しを処理経路に挟む構成は禁止)

### 4.4 競技環境の再構築

選手の操作で接続性を失った等、競技環境を初期状態に戻したい場合は CFn スタックを
削除して再作成する。再構築以前に加えた変更の移行は各チームの責任で行う。

サーバの停止・再起動は AWS マネジメントコンソール / API から自由に行ってよい。
ただし **競技終了時に 3 台すべてが起動状態である必要がある** (= 1 台でも停止していると
追試で再起動確認ができず失格となる)。

## 5. 参考実装

### 5.1 参考実装の言語

参考実装は **Rust のみ** を提供する。他言語実装の同梱はない。

### 5.2 ソース配置と起動

ソースは AMI 上の `/home/isucon/webapp/` に配置されている。systemd unit 経由で
起動しており、初期状態では debug build (`cargo run`) で立ち上がる構成になっている。

```sh
sudo systemctl status nrb2026.service
sudo systemctl restart nrb2026.service
sudo journalctl -u nrb2026.service -f
```

### 5.3 データベース (MySQL)

参考実装では MySQL 8.0 を利用する。

- データベース名: `nrb2026`
- 接続ユーザ: `isucon` / 認証: `mysql_native_password`

```sh
sudo mysql nrb2026
```

スキーマと初期データは `webapp/sql/` 以下に同梱されている。`POST /api/initialize` で
ベンチマーカーが想定する初期状態に戻る。

### 5.4 プッシュ通知

参考実装は、保存された検索条件 (saved_search) が match したキャンペーンが「残り 1 人で
募集終了」状態に遷移した瞬間に、対象ユーザーに対してプッシュ通知を送る。通知サービスの URL は
`POST /api/initialize` の `notification_webhook_url` フィールドでベンチマーカーから渡される。

#### 送信契機と宛先

- **契機**: あるキャンペーンが `current_count == goal_count - 1` に遷移した join 成功
  直後に送る (= 「残り 1 人で約定」状態に入った瞬間)。
- **宛先**: 自分の saved_search の tag 集合が、そのキャンペーンの tag 集合に **すべて含
  まれている** ユーザー全員 (= ユーザーがその saved_search の tags で `GET /api/campaigns`
  を AND 検索したらこのキャンペーンが結果に含まれる、という条件と等価)。同一ユーザーが
  複数の saved_search で match しても、`(user_id, campaign_id)` ペアごとに **高々 1 回**
  だけ送る。
- **遅延は許容される** (= 「残り 1 人」状態を抜けたあとに届いてもよい)。

#### req

```http
POST <notification_webhook_url> HTTP/1.1
Content-Type: application/json

{
  "type": "campaign_closing_soon",
  "user_id": "<通知の宛先ユーザー ID>",
  "campaign": {
    "id": "a0ed477b-cbca-4611-8a68-1eb1caf7380d",
    "name": "ナイスな椅子、ナ椅子",
    "description": "この椅子はとてもナイスで、座り心地が最高です",
    "price": 10000,
    "goal_count": 10,
    "current_count": 9,
    "tags": ["nice", "comfortable"],
    "status": "open",
    "created_at": "2026-05-01T12:00:00.000Z",
    "last_joined_at": "2026-06-01T12:00:00.000Z"
  }
}
```

`campaign` snapshot には `image` および hash 系フィールドは含めない (画像取得は
`GET /api/campaigns/{id}/image` 経由のみ)。

#### res

`201 Created`、空 body。

#### クリティカルエラー (重複送信)

同じ `(user_id, campaign_id)` の通知が 2 回以上届くと、その走行は **クリティカル FAIL**
となる (§ 6.4 参照)。同一ユーザーへの重複通知はエンドユーザーへの迷惑であり、本問題では
これを許さない。

#### ベンチマーカー走行時と手元動作確認

ベンチマーカー走行時は bench 自身が webhook receiver を提供し、`(user_id, campaign_id)`
重複検査を含む整合性検査を行う。`notification_webhook_url` は bench が initialize 時に
渡す。

参加者が手元で webapp を起動して挙動を観察したい場合、Python stdlib のみで動く最小
receiver を立てれば 201 を確実に返せる:

```sh
python3 - <<'PY'
from http.server import BaseHTTPRequestHandler, HTTPServer

class H(BaseHTTPRequestHandler):
    def do_POST(self):
        n = int(self.headers.get("content-length", "0"))
        print(self.rfile.read(n).decode())
        self.send_response(201)
        self.end_headers()

HTTPServer(("0.0.0.0", 8090), H).serve_forever()
PY
```

## 6. ベンチマーカーの実行

### 6.1 構成

ベンチマーカー (および isuwari、benchwarmer) は AMI に同梱されており、競技用 VPC 内の
ベンチマーカーノード (`192.168.0.100`) で動作する。競技用サーバー (`192.168.0.11` /
`.12` / `.13`) との通信はすべて VPC 内の private subnet 内で完結する。

ポータルからの負荷走行ジョブは ISUNARABE2 ポータル → benchwarmer → bench process の
順で起動される。選手が直接 bench バイナリを叩いてスコアを稼ぐ経路は無く、
スコアはすべてポータルに記録される。

### 6.2 走行のリクエスト

ポータルの「ベンチマーク実行」フォームから target サーバーを選び実行する。

- 1 度に 1 走行まで。RUNNING の間は新しい走行を開始できない
- target サーバはチーム内で自由に選んでよい (= ベンチを当てる対象を切替可)

### 6.3 走行の流れ

1. 初期化 (`POST /api/initialize`、30 秒タイムアウト → 超過は 0 点)
2. アプリケーション整合性チェック (pretest)
3. 負荷テスト (60秒)
4. 最終チェック (観測した約定キャンペーンの参加者の一部に対して `/charges` を突合)

初期化または整合性チェックに失敗した場合、その走行は即時 FAIL となる。

通常リクエスト (= 初期化以外) の per-request タイムアウトは **10 秒**。超過は 1 件のソフトエラー
として計上する (§ 6.5)。

負荷テスト終了時点で進行中だった HTTP リクエストは強制切断される。

### 6.4 クリティカルエラー (1 件で FAIL)

以下のクリティカルエラーは bench が 1 件でも検出した時点でその走行を即時 FAIL とする:

- 二重課金 (1 participant に対し charges が 2 件以上)
- 通知の重複送信 (同じ `(user_id, campaign_id)` ペアの通知が複数回届く、§ 5.4 参照)
- `goal_count` 超過参加 (`current_count > goal_count`)
- 課金漏れ (closed なのに participants の charges が無い)
- 与信枠超過観測 (`GET /api/me` で `credit_used > credit_limit` が観測された)
- 与信不足 join 成功 (= bench が「枠超過」と確信した join に対し webapp が 200 を返した)
- 与信契約違反 (= bench が「枠は足りる」と確信した直後の同じ枠範囲の join に対し
  webapp が 402 を返した)
- 画像不一致 (`GET /api/campaigns/{id}/image` の body bytes が POST した bytes と異なる)

FAIL となった走行のスコアは 0 点として記録される。

### 6.5 ソフトエラー (件数閾値で FAIL)

以下をソフトエラーとして 1 件ずつ計上する:

- リクエストタイムアウト (per-request 10 秒超過、§ 6.3)
- ステータスコード不一致 / レスポンス形式不正
- 画像系の `Content-Type` / `ETag` / `If-None-Match` の挙動不一致
- 画像系の負例 probe (400 / 401 / 404 / 413) の期待外れ
- その他、整合性に直結しない期待外れ

ソフトエラーが **50 件** に達した時点でその走行を FAIL とする。

### 6.6 スコア計算

加点モデル:

- 約定したキャンペーン (`status: closed`) に参加していた user 数 × **1000 点**
- 1 ユーザーが複数 campaign で約定した場合、campaign 数だけ加点される

減点 / FAIL:

- ソフトエラー 1 件あたり **-100 点**。素点から減点した結果が
  負になる場合は 0 点に丸める
- ソフトエラー 50 件到達で FAIL (§ 6.5)
- クリティカルエラー 1 件で即 FAIL (= スコア 0 として記録)

最終スコアは **競技時間中に最後に行った負荷走行の結果** を採用する。複数走行の平均や
最高は採用しない。最後の走行が FAIL であった場合、最終スコアは無いものとして扱う。

## 7. 追試

### 7.1 方針

追試は主催者の手動運用で行う。判定は合同練習会としての性格を踏まえ、機械化を最小限に
とどめる。

### 7.2 手順

主催者は以下を順に確認する:

1. **再起動 (1 回目)**: ポータルから 3 台すべてを再起動する。1 台でも再起動できない
   サーバーがある場合、追試は実施できず失格となる
2. **代理ベンチ走行**: 主催者が代理でベンチを起動する。FAIL であれば失格。スコアの
   絶対値および本走スコアとの比較は参考情報として記録するが、「再現スコアが本走の
   何 % 以上」のような機械的な閾値判定は行わない
   - 追記: 追試の負荷走行対象は、対象競技時間中に最後に行った負荷走行対象のサーバーとする
3. **再起動 (2 回目) と永続性確認**: 3 台を再度再起動し、競技中・代理ベンチ走行中に
   書き込まれたデータが取得できることを確認する。データが消失している場合は失格
4. **フロントエンド確認**: 競技用サーバーにブラウザでアクセスし、フロントエンドが
   正しく表示されることを確認する。アクセス不能、もしくは構造がリファレンス実装と
   異なる / 意図しないデータが表示されている場合は失格

失格判定は主催者の判断による。本イベントは合同練習会としての性格上、機械的に失格を
確定するのではなく、状況を見て主催者が決定する。

### 7.3 競技終了から追試完了までの選手の操作

- 競技終了後、主催者からアナウンスがあるまで競技環境のシャットダウン・停止・削除は
  行わないこと (= 3 台とも起動状態を維持する)
- 競技時間中の再起動・一時停止は構わない。ただし、競技終了時点で全 3 台が起動して
  いない場合、追試できず失格となる
- アナウンスを待たずに削除した場合、結果として失格となっても主催者は救済しない

### 7.4 追試完了後

- 追試完了および結果発表後、各チームは自身の AWS アカウント上の競技環境を削除する
  責任を負う
- 削除を行わなかったために発生した費用について、主催者は一切の責任を負わない

## 8. 禁止事項 (サマリ)

詳細はレギュレーションを参照。要点のみ再掲する:

- 競技時間中・追試完了前に、問題内容 / 解法 / 得点情報 / その他の競技にかかる情報を
  自チーム外に開示・共有すること
- 他チームとの結託、相互援助、得点情報の交換
- 他チームへの妨害行為 (DoS / SSH 不正アクセス試行 / portal への過剰負荷など)
- 主催者ベンチマーカー以外の方法でスコア機構を欺くこと
- ベンチマーク走行中、お題のアプリケーションが外部リソースに依存してリクエスト処理を
  行うこと

## 9. 改訂

本マニュアルは競技開始時刻まで予告なく改訂することがある。競技開始後の改訂は、
競技性に影響する重大な不備が発見された場合に限り、portal および Discord で全選手に
通知のうえ実施する。
